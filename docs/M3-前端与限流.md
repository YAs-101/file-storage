# M3 · 前端与限流

> 日期：2026-10-30
> 状态：完成并验证

---

## 一、这一阶段解决的问题

M1 / M2 之后，服务只能通过脚本和 curl 使用。M3 补两件事：

| 项 | 为什么必须做 |
| :--- | :--- |
| 单文件前端 | 断点续传、秒传、引用计数这些设计用 curl 演示不出来，必须有一个能看见进度、能中途刷新页面的客户端 |
| 限流 | 服务端此前对并发完全无保护：一个客户端开 200 并发就能把磁盘 IO 和 Tomcat 线程池吃满 |

---

## 二、限流：两个维度，两种算法

### 2.1 分片上传：限并发，不限 QPS

一次 1 GB 上传天然产生 200 个分片请求。按 QPS 限流的话，**一次正常上传本身就会被判定为攻击**。

真正压垮服务端的是「同时有多少个 5 MB 在写盘 / 在传 S3」，这个数与文件大小无关，只与客户端并发度有关。

| 参数 | 默认值 | 含义 |
| :--- | ---: | :--- |
| `rate-limit.chunk-concurrency` | 12 | 单用户同时在飞的分片请求上限 |
| `rate-limit.chunk-window-seconds` | 30 | 成员存活窗口，超时被裁掉（自愈用） |

12 这个数是前端默认并发（8）的 1.5 倍：正常使用永远撞不到，只有客户端开几十并发或被人刷时才会触发。

### 2.2 为什么不用「计数器 + TTL」

这是最常见的写法，一个整数键 `INCR` 后 `EXPIRE`。它在这个场景下有两个说不清的缺口：

1. **释放不幂等**。客户端超时重试、网关重发都会让同一次请求走两遍 `finally`，把计数多减一次，额度被凭空放大。要靠「减到负数就不减」补，但那只是把错误藏起来。
2. **TTL 是全局的**。只要还有请求在跑，续期就意味着崩溃残留永不清；不续期则长上传期间计数整体过期，额度同样虚增。两种取舍都不干净。

改用 **ZSET 存每个飞行中请求的进入时间戳**，一个请求就是一个成员：

```lua
-- 抢额度
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now - win)   -- 裁掉过期的
if redis.call('ZCARD', KEYS[1]) >= limit then return 0 end   -- 数一下还有几个在飞
redis.call('ZADD', KEYS[1], now, ARGV[4])
redis.call('PEXPIRE', KEYS[1], win)
return 1

-- 还额度
redis.call('ZREM', KEYS[1], ARGV[1])
if redis.call('ZCARD', KEYS[1]) == 0 then redis.call('DEL', KEYS[1]) end
```

- **释放幂等**：`ZREM` 同一成员多次无副作用
- **过期与键解耦**：按时间戳裁剪，不依赖「键整体何时过期」
- **不会负库存**：没有计数器，不存在减过头的可能

每用户最多十几个成员，内存代价可忽略。

### 2.3 token 必须由服务端生成

如果用请求头里的 `X-Request-Id` 当成员名，客户端只要在并发请求里填同一个值，`ZADD` 就退化成覆盖写而非新增，计数永远是 1 —— **限流被完全绕过**。

所以 token 由 Filter 内部生成（`rid + "#" + 进程内自增序号`），不经过任何外部输入。

### 2.4 init：限「未完成会话数」，不限次数

`init` 的风险不是并发，是**写放大**：每调一次就往 `upload_task` 写一行，而这张表没有定时清理，刷起来是永久膨胀。

| 参数 | 默认值 | 维度 |
| :--- | ---: | :--- |
| `rate-limit.max-active-sessions` | 50 | 资源：单用户未完成（状态 0/1/2）且未过期的会话数 |
| `rate-limit.init-per-minute` | 120 | 速率兜底 |

**按次数限是错的**，这一点是被自己的回归测试打出来的：最初定 30 次/分钟，结果跑一轮全量回归（4 套脚本 + 合并校验）就撞限，`test_merge_verify` 直接 1011 失败。

按会话数限则不会误伤：正常用户传完一个文件，会话变终态、不再占额度，批量上传 100 个文件也不会撞；而恶意用户能在表里堆出的活跃会话数被硬性封顶。

两种拒绝原因返回不同的 `msg`，用户才知道该去清理会话还是该等一分钟。

### 2.5 降级：fail-open

Redis 不可用时放行并记 WARN。理由：限流是保护性设施，不该成为可用性的单点；真到 Redis 挂了，合并锁也拿不到，上传链路本来就会失败。

## 三、三个被测试打出来的真问题

限流写完之后第一版测试只过了 11/14 条，剩下三条都是真实缺陷，不是测试写错。

### 3.1 限流拒绝时，客户端可能收不到 1011

**现象**：24 个慢速上传的请求里有 23 个报 `WinError 10053`（连接被中止），只有 1 个拿到业务响应。

**原因**：服务端在 Filter 里就拒绝了，**不会去读请求体**。Servlet 容器对未读部分有 swallow 上限（Tomcat 的 `maxSwallowSize`，默认 2 MB），超过就直接关连接而不吞掉。客户端此时还在 `send`，于是收到 RST 而不是那个 `{"code":1011}`。

**结论**：这不是 bug，是 HTTP 的固有行为。处理方式是**客户端把「传输中断」与 `1011` 一视同仁地退避重试**——前端的 `retriable()` 已经把 `code === undefined`（网络层错误）归入可重试。

要彻底避免，客户端可以用 `Expect: 100-continue`：服务端拒绝时回最终响应而不是 `100`，客户端就不发 body。M3 没做，记在这里。

### 3.2 并发写同一个分片会撞文件占用

**现象**：24 个线程并发 `PUT` 同一个 `chunkIndex` 时，混进 10 个 `1008`。

**原因**：同一序号就是同一个物理文件，Windows 上并发覆盖写会撞文件占用。测出来的是文件系统行为，不是限流行为。

**结论**：测试要构造「24 个并发请求打同一用户的额度」，但不能让它们写同一个文件。改成先 `init` 24 个独立小文件、每个线程打自己的 `uploadId`。**这也说明「幂等覆盖写」在并发下并不是免费的**——单客户端重传没问题，多客户端同时重传同一片会有一个拿到 1008，需要重试。

### 3.3 「每分钟次数」这种限法会误伤正常行为

见 2.4。这是唯一一个**设计本身错了**的问题，不是测试的问题。

## 四、前端：三个必须写对的地方

单文件 `static/index.html`，CSS/JS 全内联，零构建。`mvn spring-boot:run` 之后直接打开 `http://localhost:8080/` 就能用。

### 4.1 MD5 必须自己实现增量版

`crypto.subtle.digest` 只接受一次性完整输入。1 GB 文件塞进 `ArrayBuffer` 会直接把标签页打爆。而 MD5 是不可复合的（不能由分片哈希拼接出整文件哈希），所以只能自己写一个支持 `update()` 的流式实现（RFC 1321，约 120 行）。

代价是自己实现的哈希算错了整条链路都会静默报废（上传能成功，但秒传永不命中、校验总是 1006）。所以页面启动时对两个标准向量做自检：

```
md5("")    === d41d8cd98f00b204e9800998ecf8427e
md5("abc") === 900150983cd24fb0d6963f7d28e17f72
```

不通过就在控制台报错并弹提示。

### 4.2 并发池必须是全局的

第一版是「每个上传任务 8 路」。用户同时拖 4 个文件时，四个任务一起跑就是 32 个并发分片，直接撞上服务端 12 的限额，页面上会看到一片重试。

改成全局信号量：无论排了多少个任务，**同时在飞的请求数恒定为 8**。

### 4.3 断点续传的入口是「重新拖同一个文件」

不持久化上传进度到 localStorage，因为分片数据在 `File` 对象里，刷新页面后对象就没了，存了 `uploadId` 也发不出分片。

正确做法是重新选同一个文件：`init` 用 `fileMd5 + fileSize` 判定，返回**同一个 `uploadId`** 和已收到的分片序号列表 `uploaded`，客户端只补缺失部分。页面上把这句写在拖拽区的副标题里：「同一文件重复拖入会自动续传」。

## 六、已知边界

| 边界 | 说明 |
| :--- | :--- |
| 拒绝时可能收到连接重置 | 见 3.1。客户端按网络错误重试即可；要彻底避免需 `Expect: 100-continue` |
| 限流窗口内可能短暂虚高 | 某个请求处理超过 30 秒时会被裁掉，真实并发可临时略超限额。可接受：窗口是自愈机制，不是精确配额 |
| 下载接口未限流 | 下载是单请求流式传输，不是「高频小请求」形态，风险模型不同，M4 视压测结果再定 |
| 前端用 blob 下载 | 大文件会占内存。演示够用，正式方案应走流式（StreamSaver / 服务端直链） |
