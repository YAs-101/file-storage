# M2 多后端路由

> 解决的问题：`storage.type` 一改，老数据全部读不到。
>
> 提交范围：`StorageRegistry`、`FileController` / `FileServiceImpl` / `UploadServiceImpl` 按记录取后端、
> `upload_task.storage_type`、启动台账自检、`check_multi_backend.py`。

---

## 一、问题

M1 的存储抽象只做到「换实现」：`StorageConfig` 按 `storage.type` 产出一个 `FileStorage`，
业务代码注入它，一行不改就能切后端。这个抽象在「库内数据全部在同一个后端上」时才成立。

数据是持久的，配置是易变的。切到 S3 的那一刻，10 月 21–22 日上传的 25 条 LOCAL 记录就再也读不到——
不是数据丢了，是代码不再往那个后端看。

三处具体缺口：

| 缺口 | 表现 | 隐蔽程度 |
| :--- | :--- | :--- |
| 读路径不看 `file_info.storage_type` | 老文件点开返回 `1008`，看着像对象丢失 | 高：日志说「对象不存在」，实际在另一个后端上 |
| 删除按当前配置的后端做 | 真对象留在老后端（物理泄漏），同时可能在当前后端上删掉一个**同键**的无关对象 | 极高：接口返回成功，两种后端各自的回归测试都是绿的 |
| `upload_task` 没有 `storage_type` | 进行中的会话切后端后，已传分片在旧后端，续传记录在库里 → 假进度，永远合并不出来 | 高：表现为「一直传不完」 |

「删除错后端」这条是这个设计里唯一会造成**数据丢失**的路径。原因是 `objectKey` 由 MD5 决定
（`ObjectKeys.ofMd5`），两个后端上完全可能挂着同一个键。删错的后果不是「没删掉」，而是「删掉了别人的」。

---

## 二、方案

写入按配置，读取按记录。

```
                     ┌──────────────────────────┐
  写路径             │  StorageRegistry         │            读/删路径
  (init/上传/合并)   │  defaultStorage()        │            (download/delete)
        ────────────>│  of(record.storageType)  │<────────────
                     └──────────┬───────────────┘
                                │ 惰性装配
                  ┌─────────────┴─────────────┐
                  ▼                           ▼
          LocalFileStorage            S3FileStorage
          (storage/data)              (S3 桶)
```

`StorageRegistry` 三个约定：

1. **注册不等于创建。** 两个实现都注册进工厂表，但只有真的读到某后端的数据时才创建客户端。
   否则本地只跑 `storage.type=local` 也要先连一次 S3，没起对象存储就起不来。
2. **默认后端必须当场装配。** 配置项写错在启动时炸，比在第一次上传时炸便宜得多。
3. **装配失败的后端记入 `broken`，不反复重试。** S3 端点写错时每次重连要等超时，
   不记的话每个请求都卡几十秒。

业务层的取法：

| 路径 | 取值来源 | 原因 |
| :--- | :--- | :--- |
| 上传分片 / 合并 / 合并校验 / 删分片 | `upload_task.storage_type` | 会话归属在 `init` 时定死，切配置不影响进行中的会话 |
| 下载 | `file_info.storage_type` | 对象实际所在的后端 |
| 删除（引用归零） | `file_info.storage_type` | 同上，这是唯一会造成数据丢失的路径 |
| 新写 `file_info` | 本次合并所用后端 | 合并产物落在哪个后端，记录就指向哪个 |
| 新写 `upload_task` | `registry.defaultType()` | 会话从建立那一刻起归属固定 |

## 三、实现要点

### 1. 数据模型

`upload_task` 增加 `storage_type varchar(16) not null default 'LOCAL'`。
历史数据按 `LOCAL` 处理，再按分片的**物理位置**修正了 2 条实际在 S3 上的进行中会话——
只按默认值填会让这两个会话永远合并不出来。

### 2. 唯一索引冲突分支的判断

`writeFileInfo` 撞上 `uk(file_md5, file_size)` 时，要决定自己刚合并出的那份是不是多余的：

```java
boolean sameObject = exist.getObjectKey().equals(objectKey)
        && (existType.isEmpty() || existType.equals(storageType));
if (!sameObject) {
    storage.deleteObject(objectKey);
}
```

必须同时比 key 与后端。只比 key 的后果：库里引用指向 LOCAL 上的 `K`，
本次在 S3 上也合并出一份 `K`，判定「同键」→ 不删 → S3 上那份永远没人引用，空间泄漏且查不出来。
反过来只比后端更错，会把自己的产物删掉。

### 3. 启动自检

`StorageStartupCheck` 在 `ApplicationRunner` 里打一张台账，按记录（不是按配置）列出：

```
存储台账（默认后端=S3，已装配=[S3]，已注册=[S3, LOCAL]）
  LOCAL   可用 25   条 197.0 MB
  S3      可用 24   条 192.0 MB
  进行中会话 LOCAL   14 个（分片已落该后端，切后端不影响它们）
  进行中会话 S3      2 个（分片已落该后端，切后端不影响它们）
```

若某后端未注册或装配失败，该行标注 `<- 本进程不可读`，并额外 WARN 一条汇总条数。
**只报告不拦截**：「有几个后端的数据」是历史事实，不是配置错误，让人起不来服务是更糟的选择。
真正该拦的是默认后端装不上，那个在 `StorageRegistry` 构造时就抛了。

### 跨后端读写

| :--- | :--- | :--- |
| 跨后端读 | 服务跑 S3 模式，下载 `storage_type=LOCAL` 的 16 MB 文件 | `200`，MD5 与 `file_info.file_md5` 一致 |

## 五、已知缺口

| 缺口 | 说明 | 影响 |
| :--- | :--- | :--- |
| 秒传跨后端 | `init` 按 `md5 + size` 命中已有记录就直接建引用，可能命中另一个后端的记录 | 读没问题（按记录路由）；但新引用指向老后端，默认后端的对象数不会增长。属设计取舍：去重优先于落位 |
| 两套实现共享一份配置 | 同一进程内 `LocalFileStorage` 与 `S3FileStorage` 读同一份 `storage.*` | 无法给不同后端配不同的 `base-path`；多端点 / 多桶不在本阶段范围 |
| 删除失败只能记日志 | 删对象在 `afterCommit`，已脱离事务 | 留 `status=2` 但对象仍在的残留，靠 `audit_objects.py` 定期核对 |
| 未装配后端无法预判 | 惰性装配，只有真读到才知连接是否可用 | 台账说的「已注册」不等于「连接通」；首次访问可能才暴露端点错误 |

## 六、怎么讲

一句话：**存储抽象的第二层是「多实现共存」，不是「换个实现」。**

第一层解决的是「代码不依赖具体后端」；第二层解决的是「数据不依赖当前配置」。
面试上被问「你怎么做存储抽象」，答第一层只能证明会写接口；能说清第二层，才证明想过
「配置会变、数据不会自己搬家」这个真实约束。

三个可以展开的点：

1. **为什么删除比读取危险。** 读错后端得到 404，是可观测的失败；删错后端得到 200，
   是静默的数据丢失。而 `objectKey` 由内容 MD5 决定，天然跨后端同键。
2. **为什么路由粒度是「记录」而不是「会话」。** 读取的输入是 `user_file`，它指向 `file_info`，
   记录上有 `storage_type`；会话是写入侧的临时状态，两者生命周期不同，不能共用一个归属。
3. **为什么自检只报告不拦截。** 数据状态与配置错误要区别对待：前者是历史事实，
   拦了只是把问题推给运维；后者是当下错误，必须当场暴露。
