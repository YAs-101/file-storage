### 两条容易被混为一谈的结论

1. **下载链路没坏**。库里 `user_file=444` 的 3 MB 内容与 `file_md5` 完全一致、`Content-Length` 也一致，但文件头是随机字节、没有 `%PDF-` 与 `%%EOF`。它由 `test_download.py` 用 `os.urandom` 造出并命名为 `.pdf`。同名的 `userFileId=468`（同样 3 MB）文件头为 `%PDF-1.4`，可正常打开——名字和大小一样，差别只在内容。
2. **状态码错了会伪装成「文件损坏」**。`GET /api/file/abc/download` 原返回 `HTTP 200 {"code":400,...}`，前端 `resp.ok` 判成功，把 JSON 存成 `.pdf`，用户看到的症状与第 1 条完全一样。修法：URI 以 `/download` 结尾才按真实状态码回（400/403/404/413，1010→503，其余 500），其他接口维持 200 不变——**用 URI 判断而非返回类型，因为参数绑定失败时没有任何返回类型上下文可用**。

## 今天踩的坑

- **固定测试样本会命中秒传**。把 `test_download.py` 的样本从随机字节改成确定性 PDF 后，第二次运行直接走秒传（`init` 返回 `uploadId=None`），而脚本后续仍按「需要上传」的路径走，断言失败。最终用 `salt` 让每次内容不同，同时保持 PDF 结构合法与长度精确对齐。
