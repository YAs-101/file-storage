## 压测口径

**对外一律用 2026-11-01 复测数字**（12 并发 = 服务端上限，零重试，三次中位数）：

| 指标 | 512 MB | 1 GB |
| :--- | ---: | ---: |
| 墙钟总耗时 | 2.48 s | 5.81 s |
| 上传阶段 | 0.52 s（984 MB/s） | 1.10 s（931 MB/s） |
| 合并阶段 | 1929 ms | 4669 ms |
| 有效吞吐（含合并） | 206 MB/s | 176 MB/s |

秒传必须给两个口径，只给一个会失真：关闭限流 222–303 QPS（中位 ~260）；按生产默认 `init-per-minute=120` 则被钉在 120 次/分钟/用户。

11-02 复核时这些数字整体偏低（512 MB 中位 3.17 s、1 GB 11.4–12.2 s），已确认不是代码问题：仓库从 `6f764c8` 起没有服务端改动，且 **512 MB 合并还能跑到 ~210 MB/s、1 GB 合并掉到 ~95 MB/s**，体积涨 2 倍耗时涨 4.5 倍，正是 QLC 写速悬崖（10/31 抽测 `1538/1559/1802/95/1875/197 MB/s`）的表现；当天连压多轮累计写入数 GB，盘一直停在慢速区。另一个变量是空闲物理内存只剩 2.4 GB / 15.7 GB，页缓存被挤掉之后上传阶段读临时文件也慢。**这组数字不作为口径，只作为同一套行为结论的复现记录。**

## 已知局限（设计取舍，不是待修 bug）

| 局限 | 影响 |
| :--- | :--- |
| 秒传跨后端命中老后端记录时新对象不落默认后端 | 数据可用，只是不均衡 |
| 同进程两个后端实现共享一份 `storage.*` 配置 | 覆盖粒度粗 |
| `afterCommit` 删对象失败只记日志 | 极端情况留无主对象，靠 `audit_objects.py` 兜底 |
| 过期会话的分片记录无自动回收路径 | `upload_chunk` 会积累孤儿行，需人工或定时任务 |
| 鉴权靠 `X-User-Id` 请求头 | 演示用，无真实登录 |
| 未做真实 S3 验证 | 绝对性能不可外推 |

## 未验证

- **真实网络吞吐**：全部数字是同机回环，客户端与服务端抢同一块盘
- **真实 S3 的合并代价**：S3Mock 在本地真拼字节，真实 S3 的 `CompleteMultipartUpload` 只改元数据，耗时结构完全不同
- **多机部署**：限流依赖 Redis 已就绪，但没验证跨节点一致性
- **1 GB 堆峰值与 GC**：11/02 决定不再采集，实现自 M1 起未改动，引用时标 M1 数据即可

## 后续若要继续

优先级按性价比排：接真实对象存储（换 `storage.s3.endpoint` 跑同一份 `verify_s3_endpoint.py`）→ 过期会话分片定时回收 → 接 Spring Security 换掉 `X-User-Id` → 秒传跨后端均衡。再加功能对求职呈现的边际收益已经很低，时间应该给简历与面试准备。
