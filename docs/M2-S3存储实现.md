# M2：S3 存储实现

## 结论

`S3FileStorage` 已实现并接入，`storage.type` 切换即生效，业务层零改动。本地与 S3 两种后端跑同一套 58 条断言，全部通过（e2e 5 / 下载 16 / 删除 13 / 负向 24）。

但性能数据要看清楚一件事：**S3Mock 的 `CompleteMultipartUpload` 是真在本地拼接字节，真实 S3 只是改元数据。** 所以本文的合并耗时是「模拟出来的成本」，不能当成 S3 的实际表现。

## 对象布局

```
{chunkPrefix}/{uploadId}/{chunkIndex}.part   临时分片
{objectKey}                                  最终对象（md5 前2位/其余30位，与本地实现一致）
```

分片和最终对象同桶不同前缀。不用多桶：多一个桶就多一套权限策略，部署与授权成本翻倍，而前缀隔离已经够 `deleteChunks` 按前缀批量清理。

## 五个方法的映射

| FileStorage | S3 原语 | 与本地实现的差异 |
| :--- | :--- | :--- |
| `saveChunk` | PutObject | 拿到请求体长度就流式转发；拿不到才落临时文件 |
| `objectSize` / `objectExists` | HeadObject | 404 统一翻译成「不存在」而不是异常 |
| `openRange` | GetObject + `Range: bytes=a-b` | 206 / Content-Range 由 S3 原生给出，下载方法不用改 |
| `deleteObject` | DeleteObject | 本身就是幂等（对象不存在也返回 204） |
| `mergeChunks` | Create + UploadPartCopy ×N + Complete | 数据在存储内部搬，本进程不碰字节 |

## 三个关键实现决定

**一、合并走 UploadPartCopy，不用 Get + Put。**

本地实现要把 N 个分片读一遍写一遍，1 GB 光搬运就吃了 82% 的墙钟。`UploadPartCopy` 让数据在存储内部走，本进程只发请求。落代码之前先用 curl 单独验过这条语义：5 MB + 1 MB 两片服务端拼接后，字节与 MD5 与本地 `cat` 的结果完全一致。

**二、part copy 必须并发。**

partNumber 从 1 开始且连续，和分片序号不是同一个东西（分片序号由客户端定，partNumber 由 S3 定）。`futures` 按提交顺序收集，取回来天然是升序，Complete 不会报 `InvalidPartOrder`。

实测单次 part copy 约 180 ms，瓶颈在请求往返而不是数据量，串行发 52 片要 4.4 秒；8 路并发后降到 0.57 秒，约 7 倍。线程数由 `storage.s3.merge-copy-threads` 控制，默认 8。

**三、失败必须 abort。**

未完成的 multipart 在 S3 上不可见但占存储、会计费，不 abort 就永远清不掉（生命周期规则是另一回事）。所以 `mergeChunks` 里所有异常分支——包括分片缺失这种业务异常——都先 abort 再抛。

## 上传为什么需要 Content-Length

PutObject 不接受未知长度。猜大了 S3 会一直等剩下的字节直到超时，猜小了直接截断。

分片接口传的是原始二进制（`application/octet-stream`），不是 multipart，所以 `request.getContentLengthLong()` 就是分片真实大小。把它一路透传到存储层（`FileStorage.saveChunk` 多了 `contentLength` 参数），S3 实现就能 `RequestBody.fromInputStream(in, len)` 边读边发，一个字节都不落本地。chunked 传输时它是 -1，退化成先落临时文件再上传。

流式路径下用 `CountingInputStream` 数实际读出的字节数，保证「客户端声明的长度」与「真实写入量」对得上——不一致时仍然会走 `written != expected` 的校验报 1004。

## 实测：256 MB / 8 并发

| 阶段 | 本地（M1 L3） | S3（S3Mock） | 说明 |
| :--- | ---: | ---: | :--- |
| 上传 | 0.37 s / 693 MB/s | 2.54 s / 100.6 MB/s | S3Mock 的 PUT 吞吐上限约 100 MB/s |
| 合并——copy | — | 0.57 s | 52 片，8 路并发 |
| 合并——complete | — | 4.93 s | **S3Mock 真的在拼字节，约 50 MB/s** |
| 合并合计 | 1.22 s | 7.58 s | |
| 墙钟 | 1.63 s | 10.72 s | |
| 有效吞吐 | 156.8 MB/s | 23.9 MB/s | |

对照数据：

- **串行 copy 版本**合并 9.54 s，并发后 7.85 s；拆分计时后确认 copy 从约 4.4 s 降到 0.57 s，剩下的全是 complete。
- **`verify-merged-md5`**：`auto`（用 ETag 指纹）与 `always`（全量读回）差约 1.25 s，见下文「按后端分策略」。M1 记录里的 `true`/`false` 对照要按这套新数值理解，不要混用。

## 这份数字能说什么、不能说什么

**能说：**

- 换后端不改业务代码这件事是真的——`FileController` 的下载、`UploadServiceImpl` 的合并与三层幂等、`FileServiceImpl` 的引用计数，一行都没动。
- part copy 的并发是必要优化，串行会随分片数线性恶化；1 GB 是 200 片，串行要 36 秒。
- 流式上传省掉的是每片一次冗余本地写，代码更短，路径更直。

**不能说：**

- **不能说「S3 的合并比本地快」。** 4.93 秒的 complete 是 S3Mock 的实现行为。真实 S3 的 `CompleteMultipartUpload` 是元数据操作，不搬数据。这条结论要等接真实端点（或换 MinIO）才能测。
- **不能说「S3 模式吞吐 23.9 MB/s」。** 这个数被 S3Mock 的 PUT 吞吐和 complete 拼接同时限制，两头都不是真实 S3 的特征。

准确表述应该是：**在 S3Mock 上，合并的瓶颈从「应用侧数据搬运」变成了「存储端拼接」，而后者在真实 S3 上不成立。** M1 那句「瓶颈在合并、占 82%」不能外推到 M2。

## `verify-merged-md5`：按后端分策略

M1 里这是个布尔开关，开了就重读整文件算 MD5。当时只有本地磁盘，读的是盘；M2 之后同一行代码变成把整个对象从远端拉回来，1 GB 多一次全量出网，真实环境还计流量费。**校验本身没变，成本变了一个数量级**，所以改成三态：

| `storage.verify-merged-md5` | 行为 | 用途 |
| :--- | :--- | :--- |
| `auto`（默认） | 后端能给产物指纹就用指纹，给不出就全量读回 | 日常 |
| `always` | 一律全量读回算 MD5 | 需要完整语义时 |
| `never` | 一律不校验 | 压测对照（M1 的 L7-B 就是这么测出来的） |

### S3 的指纹怎么用

先单独验了两个事实，否则整套做法不成立：

1. multipart ETag = `md5(各 part 的二进制 MD5 串接)` + `-part数`。用 5 MB + 1 MB 两片实测，S3Mock 返回 `3fefab63…-2`，与本地按公式算出的完全一致。
2. 单段 `CopyObject` 的 ETag 就是对象内容的 MD5。

part 是 `UploadPartCopy` 从分片对象复制来的，所以 part 的 MD5 就等于分片落盘时服务端自己算的 `upload_chunk.chunk_md5`。于是校验不需要读数据：

1. `mergeChunks` 把 Complete 返回的 ETag 一并带出（`MergeResult.etag`，不额外发请求）；
2. 从 `upload_chunk` 按序号取各片 MD5，转回二进制、串接、生算，末尾加 part 数；
3. 与 ETag 比。一致即证明「拼出来的对象确实由这些分片、按这个顺序组成」——没有缺片、错序、替换。

### 收益（256 MB / 8 并发，同一实例，S3 后端）

| 策略 | 合并阶段 | 合并内部 |
| :--- | ---: | :--- |
| `auto` | 4111 ms | copy 412 + complete 3205 = 3617 ms |
| `always` | 5365 ms | 5038 ms（含一次 256 MB 全量 GET） |

省 1.25 s，约 23%。真实 S3 上这份成本还要叠加出网流量费。

### 边界

**多段路径下指纹只证明「拼装正确」，证明不了「整文件 MD5 等于客户端声明值」**——MD5 不能由分片 MD5 复合。所以「声明错误 fileMd5 的多段上传」在 S3 上会通过，在本地会被拦下。单段（小于一个分片）没有这个缺口，ETag 就是内容 MD5。

要补上这一步只能用 `always`。

ETag 不是内容指纹的后端（SSE-KMS 加密桶、部分私有实现）不会被误杀：ETag 与推算值不一致时先降级做一次全量读来裁决，只在异常路径付这份成本；推算依据不足（分片记录数与 part 数不符、ETag 格式不认识）时也退回全量读回。

### 验证

`scripts/test_merge_verify.py`，4 个场景 × 两种后端：

| 场景 | 本地 | S3 |
| :--- | :--- | :--- |
| 正常多分片（不能误杀） | 通过 | 通过 |
| 分片落盘后被同长度内容替换 | 1006 | 1006 |
| 声明错误 fileMd5（多段） | 1006 | 通过（已知语义差） |
| 单分片 + 声明错误 md5 | 1006 | 1006 |

第二个场景是核心：长度不变、只换内容，靠大小校验发现不了，只有指纹或全量读回能抓。走指纹路线时用的是 `校验=ETag(…)`，降级时是 `校验=全量读回`，证据写进「合并完成」那行日志，排障不用猜。

两个后端各跑一遍 58 条断言，仍然全过。

## 复现

```bash
# 1. 起 S3 端点
D:\Codex\s3mock-runner\start.bat

# 2. 起服务（S3 模式）
D:\Codex\file-storage\scripts\run-s3.bat
#    8080 被本机微信输入法占用时：set FS_PORT=18080 再运行

# 3. 断言（两种后端通用）
set FS_BASE=http://127.0.0.1:18080
set S3_ENDPOINT=http://127.0.0.1:9090
python scripts\test_e2e.py
python scripts\test_download.py
python scripts\test_delete.py       # 给了 S3_ENDPOINT 就 HEAD 桶，否则查本地目录
python scripts\test_negative.py
python scripts\test_merge_verify.py --backend local    # 本地后端
python scripts\test_merge_verify.py --backend s3       # S3 后端（会直接篡改桶内分片）

# 4. 压测
python scripts\bench_upload.py upload --base http://127.0.0.1:18080 --size 256 --concurrency 8
```
