### 10/25 实际结果（已完成）

分级压测 7 级，逐级施加负载，每级单独取数：

| 级别 | 负载 | 关键数据 |
| :--- | :--- | :--- |
| L1 | 16 MB / 并发 1 | 单请求基线，init 371 ms 是 JVM 预热 |
| L2 | 64 MB / 并发 4 | init 回落到 44 ms，上传阶段 380 MB/s |
| L3 | 256 MB / 并发 8 | 上传阶段 692 MB/s，合并 1217 ms |
| L4 | 512 MB / 并发 16 | 上传阶段 **1103 MB/s**，合并 2491 ms；Young GC **0 次新增** |
| L5 | 200 次秒传 / 并发 32 | 253 QPS，`ref_count` 精确 201，`file_info` 1 条 |
| L6 | 20 并发 complete | 物理合并 1 次，19 次复用成功，失败 0 |
| L7 | 1 GB / 并发 16 | 墙钟 5.84 s，有效吞吐 175.3 MB/s，堆峰值 34 MB，Full GC 0 |

压测暴露并修掉两个缺陷：

1. **20 并发 complete 有 19 个收到 `1005`**。`1005` 的语义是「请稍后查询」，客户端只能自己重试。改为失败方等待合并落地后返回同一结果（`merge-wait-ms`，默认 3 秒上限，避免合并卡死时占满线程池）。修复后 20 个请求全部拿到结果。
2. **合并后重读整文件算 MD5 是主要耗时**。1 GB 合并 4776 ms，关掉重算降到 2518 ms（省 47%）。没有直接删掉这段逻辑，而是做成开关 `storage.verify-merged-md5`，默认开——它是唯一真正生效的端到端完整性校验（分片级 MD5 只在客户端主动传 `X-Chunk-Md5` 时才校验）。

另一个发现：**瓶颈在合并，不在上传**。1 GB 上传阶段只占 18%，合并占 82%。这在 M2 换 S3 后会变化——S3 的 `CompleteMultipartUpload` 是服务端内部拼接，不需要把数据搬到本地，合并开销会大幅下降。

## 六、已决策：分片走服务端中转（A 方案）

| 方案 | 处理方式 | 结论 |
| :--- | :--- | :--- |
| **A. 服务端中转** | 前端 `POST` 分片到 Java 服务，服务端流式写入存储 | **采用** |
| B. 预签名直传 | 服务端签发 URL，前端直传对象存储 | 不做，写进 README 作为优化方向 |

选 A 的真实理由（面试可直接用）：**M1 阶段没有前端，B 方案无法独立验证**；而 A 让服务端看得到分片内容，能做文件头校验、限流、真实带宽统计。代价是服务端流量翻倍，这一点在 README 里作为已知 trade-off 写明，并给出切换路径。

A 方案的接口形态（明天写代码时照此实现，不再改）：

- `init` 返回 `{uploadId, instant, chunkSize, chunkTotal, uploaded:[]}` —— 不给预签名 URL
- `chunk` 接收 `multipart/form-data`：`uploadId`、`chunkIndex`、`file`，服务端**流式**写盘（`InputStream` → `Files.copy`，禁止 `getBytes()` 全读进内存）
- `complete` 只带 `uploadId`
