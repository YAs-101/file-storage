# M2 前置：S3 端点验证

## 结论

本地 S3 端点已跑通，`scripts/verify_s3_endpoint.py` 的 23 条断言全过。M1 的四条链路在 S3 协议下的语义和本地实现一致，`FileStorage` 的接口设计不需要改。

端点：`http://127.0.0.1:9090`，桶 `file-storage`。启动方式和依赖坑见 `D:\Codex\s3mock-runner\README.md`。

## 为什么先做这个

M2 的核心验收标准是「换存储后端不改业务代码」。这句话成立的前提是：`FileStorage` 每个方法在 S3 上都有语义等价的原语。如果某个方法在 S3 上没有对应能力，接进去才发现，业务层就得跟着改。

所以这一轮不看性能，只核语义。

## 逐条对应关系

| `FileStorage` 方法 | S3 原语 | 验证结果 |
| :--- | :--- | :--- |
| `putObject(key, in, size)` | `PutObject` | 10000 字节往返一致 |
| `objectSize(key)` | `HeadObject` 的 `Content-Length` | 大小精确 |
| `openRange(key, offset, len)` | `GetObject` + `Range` | 206 + `Content-Range` 正确；越界 416 |
| `deleteObject(key)` | `DeleteObject` | 幂等，返回 204 |
| `mergeChunks(parts, key)` | `CreateMultipartUpload` → `UploadPart` → `CompleteMultipartUpload` | 3 片共 10486784 字节，合并后内容与 MD5 全对 |

`openRange` 是这次验证的重点，因为 M1 的下载链路依赖 206 / 304 / 416 三个状态码。S3 的 Range GET 天然返回 206 和 416，`Content-Range` 格式也和本地 `ByteRange` 生成的一致，所以 `FileController` 的下载方法不用动。

## 对 M2 的两个实质影响

**一、合并开销会消失。** M1 压测的结构性结论是「瓶颈在合并，1 GB 时占墙钟 82%」，其中 `transferTo` 搬数据和合并后重读算 MD5 各占一块。S3 的 `CompleteMultipartUpload` 是服务端内部拼接，数据不经过应用进程，这两块开销在 S3 模式下都不存在。M1 的那组数字不能直接外推到 M2 的性能预期，需要重测。

**二、`storage.verify-merged-md5` 的语义变了。** M1 里它是「合并后重读本地整文件算 MD5」，在 S3 模式下要改成「Range GET 读回整对象算」，本质上还是全量下载一次，反而更贵。

更合理的做法是分片级校验前移：上传每个 part 时算 MD5 并要求客户端传 `X-Chunk-Md5`，合并后不再全量重算。S3 的 multipart ETag 是对各 part ETag 拼接后再算 MD5，不能直接当文件 MD5 用，这点要写进设计。

## 端点的适用范围

S3Mock 只做协议联调，不是生产可用服务。它跑在单进程内存/本地目录上，没有多副本、没有一致性语义、并发模型也不同。

M2 收尾时的真机验证仍要换 SeaweedFS 或云厂商 —— 但那时验的是性能和稳定性，语义已经在这里锁定过了。
