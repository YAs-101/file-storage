# M4 压测方案与首轮基线（2026-10-31）

## 一、为什么必须重测

M1 的压测数字（1GB 端到端 5.84s、上传阶段 1103 MB/s）是在**限流上线之前、单 JVM、磁盘空闲**三个条件下测的。M3 加了分片并发限制（12）与 init 会话数限制（50），这两个条件至少有一个已经变了，所以旧数字不能直接沿用。

首轮复测就出了问题：**同一个档位（512MB / 16 并发）连续跑，上传阶段吞吐从 622 MB/s 掉到 424 MB/s，合并阶段从 2.18s 涨到 8.77s。** 如果不先搞清楚原因，任何一组数字都会被当成「性能回归」，而实际是测量方法有问题。

## 二、三类失真，都有实测证据

| # | 现象 | 原因 | 修法 |
| :--- | :--- | :--- | :--- |
| 1 | 所有分片返回 `200`，`complete` 却报「分片不完整 100/103」 | 限流按本项目约定包在 **HTTP 200 的 body** 里（`{"code":1011}`），脚本只判 HTTP 状态，把被拒当成功，**静默丢 3 片** | 成功判据改为 `code == 0` |
| 2 | 分片返回 `-1`（连接重置），失败被计入分母 | 限流在请求体传输途中拒绝，服务端不读 body，容器对超出 swallow 阈值的部分直接断连 | 网络层错误纳入重试，与 `1011/1005/1008` 同等对待，指数退避 + 抖动 |
| 3 | 同一档位逐轮变慢（622 → 718 → 424 MB/s） | 压测对象留在 `storage/`：10 轮 × 512 MB = **5.1 GB**，D 盘可用空间从 30 GB 掉到 27 GB（92% 满），NTFS 分配退化 | 每轮结束清理对象；测量前固定磁盘条件 |

第 1 条最危险：**静默丢数据比直接报错难查得多**。客户端看着全绿，服务端少 3 片，最后报的是 `1003`，很容易被误判成服务端状态机的问题。

修完之后脚本会主动报告重试构成，例如：

```
重试 9 次（code=1011×6、网络层(连接重置)×3），最多次数 1
```

## 三、测量条件（不满足则数字作废）

| 条件 | 要求 | 说明 |
| :--- | :--- | :--- |
| 磁盘可用 | D 盘 ≥ 60 GB | 低于这个数，NTFS 大块分配明显变慢，实测 27 GB 时吞吐掉 40% |
| 回收站 | < 1 GB | 本机删除走回收站，不清等于没删 |
| 同机 JVM | 只留被测服务 | 多一个空闲 JVM 影响不大，但压测对象累积会 |
| 压测对象 | 每轮结束删掉 | 否则 storage 体积线性增长，见失真 3 |
| 重复次数 | 同档 3 次取中位数 | 单次噪声可达 ±30%，见下节波动 |
| 临时文件 | 记下所在盘剩余 | `bench_upload.py` 在 `%TEMP%` 生成待传文件 |

## 四、首轮基线（LOCAL 后端）

环境：i7-12700H / 16 GB / D 盘 32 GB 可用（清理后）/ 单 JVM / JDK 17.0.19。

512 MB，103 个分片，16 并发，跑 3 次：

| 轮次 | 墙钟 | 上传阶段 | 合并阶段 | 上传阶段吞吐 |
| :--- | ---: | ---: | ---: | ---: |
| 1 | 2.97 s | 0.77 s | 2157 ms | 665 MB/s |
| 2 | 2.90 s | 0.69 s | 2171 ms | 743 MB/s |
| 3 | 2.99 s | 0.69 s | 2200 ms | 743 MB/s |
| **中位数** | **2.97 s** | **0.69 s** | **2171 ms** | **743 MB/s** |

有效吞吐（含 init 与合并）177 MB/s。合并阶段占了墙钟的 73%。

## 五、限流到底花掉多少

另起一个实例（18082）把 `rate-limit.chunk-concurrency` 从 12 放宽到 200，其余配置一致，同机同时段对照：

| 实例 | 分片并发上限 | 上传阶段 | 重试次数 |
| :--- | ---: | ---: | ---: |
| 18081 | 12 | 0.69 / 0.77 s | 9 次 / 103 片 |
| 18082 | 200 | 0.69 / 0.75 s | 0 |

**结论：限流对吞吐的影响在当前量级下不可测。** 它的代价只是超并发部分的排队重试（9/103 ≈ 8.7% 的分片多跑一次），而这些重试发生在 16 并发、每次约 50 ms 退避的量级，落进合并阶段的时间窗里看不出来。

顺带否掉一个直觉：限流的「12」限制的是**同时在飞的分片请求数**，不是吞吐。把并发压到 12 以内，一次都不会被拒。

## 六、瓶颈在磁盘 I/O，不在 CPU

裸设备测（同一块 D 盘，5 MB 块 × 103）：

| 操作 | 吞吐 |
| :--- | ---: |
| 顺序写（含 fsync） | 1717 MB/s |
| 顺序读 | 636 MB/s |

对照合并阶段：2171 ms 内要完成「读 103 个分片 + 写 1 个对象 + 回读整文件算 MD5」，I/O 总量约 1.5 GB，聚合 707 MB/s，正好压在**读速 636 MB/s** 附近。

所以 M1 的判断成立且原因更清楚：**合并慢是因为同一份数据被读了两遍**（拼装一遍、校验 md5 再读一遍），不是 CPU 不够。`storage.verify-merged-md5` 在本地方盘上省不掉这次回读，只有在能给产物指纹的后端（S3 的 multipart ETag）才能真正跳过。

## 七、可外推性判定

| 后端 | 哪些数字可信 | 哪些不可外推 |
| :--- | :--- | :--- |
| LOCAL | 全部（就是真实磁盘行为） | — |
| S3Mock | 相对差异（换后端前后的结构变化） | **绝对吞吐、合并耗时**。它的 `CompleteMultipartUpload` 在本地真拼字节（约 50 MB/s），真实 S3 只改元数据 |
| 真实 S3 | — | 本机没有，未测 |

写简历或文档时，S3 侧只能表述「合并从应用侧搬运变成存储端拼接，应用进程不再碰字节」，不能写成「S3 合并更快」。

## 八、对简历数字的影响

| 原表述 | 现状 | 建议 |
| :--- | :--- | :--- |
| 上传阶段吞吐峰值 **1103 MB/s** | 本机当前复现不到，稳定值 743 MB/s | **改用 743 MB/s（512MB/16 并发）**；若要保留峰值，必须写清测试条件 |
| 1 GB 端到端 5.84 s | 今天未重测 | 待 M4 第二轮验证 |
| 秒传 253 QPS | M3 的 init 限流可能影响 | 待重测 |

结论：**能写可复现的数字，不要写峰值。** 面试官让复现时，环境差异会直接暴露。
