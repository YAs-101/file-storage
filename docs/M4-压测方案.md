# M4 压测方案与基线（10/31 首轮 · 11/01 第二轮）

## 一、为什么必须重测

M1 的压测数字（1GB 端到端 5.84s、上传阶段 1103 MB/s）是在**限流上线之前、单 JVM、磁盘空闲**三个条件下测的。M3 加了分片并发限制（12）与 init 会话数限制（50），这两个条件至少有一个已经变了，所以旧数字不能直接沿用。

首轮复测就出了问题：**同一个档位（512MB / 16 并发）连续跑，上传阶段吞吐从 622 MB/s 掉到 424 MB/s，合并阶段从 2.18s 涨到 8.77s。** 如果不先搞清楚原因，任何一组数字都会被当成「性能回归」，而实际是测量方法有问题。

## 二、三类失真，都有实测证据

| # | 现象 | 原因 | 修法 |
| :--- | :--- | :--- | :--- |
| 1 | 所有分片返回 `200`，`complete` 却报「分片不完整 100/103」 | 限流按本项目约定包在 **HTTP 200 的 body** 里（`{"code":1011}`），脚本只判 HTTP 状态，把被拒当成功，**静默丢 3 片** | 成功判据改为 `code == 0` |
| 2 | 分片返回 `-1`（连接重置），失败被计入分母 | 限流在请求体传输途中拒绝，服务端不读 body，容器对超出 swallow 阈值的部分直接断连 | 网络层错误纳入重试，与 `1011/1005/1008` 同等对待，指数退避 + 抖动 |
| 3 | 同一档位逐轮变慢（622 → 718 → 424 MB/s） | 压测对象留在 `storage/`：10 轮 × 512 MB = **5.1 GB**，D 盘可用空间从 30 GB 掉到 27 GB（92% 满） | 每轮结束清理对象；测量前固定磁盘条件 |

第 1 条最危险：**静默丢数据比直接报错难查得多**。客户端看着全绿，服务端少 3 片，最后报的是 `1003`，很容易被误判成服务端状态机的问题。

> **11/01 修正**：第 3 条把「可用空间变少」当成了原因，实际它是代理变量。同一块盘按 512 MB 分段连写 3 GB，实测速度是 `1538 / 1559 / 1802 / 95 / 1875 / 197 MB/s`——**锯齿状**，这是 QLC 颗粒 SLC 缓存写穿后进入垃圾回收的表现，与剩余空间无必然关系。今天 D 盘只有 29–32 GB 可用，上传阶段仍稳定在 931–984 MB/s。准确说法是：**这块盘存在写速悬崖，落在悬崖窗口内的那一轮会慢 5–10 倍**，所以必须多轮取中位数，而不是「留够空间就一定快」。

修完之后脚本会主动报告重试构成，例如：

```
重试 9 次（code=1011×6、网络层(连接重置)×3），最多次数 1
```

## 三、测量条件（不满足则数字作废）

| 条件 | 要求 | 说明 |
| :--- | :--- | :--- |
| 客户端并发 | **≤ 服务端 `chunk-concurrency`（12）** | 超出即必然被拒。16 并发跑 1 GB（205 片）时，重试 6 次仍有 2 片失败，整轮作废 |
| 磁盘状态 | 记录可用空间，并接受 ±5 倍波动 | 真正变量是 SLC 缓存/GC 状态，见第二节修正 |
| 回收站 | 定期清空 | 本机删除走回收站，不清等于没删（11/01 实测：清 3.5 GB 分片后 `df` 纹丝不动） |
| 同机 JVM | 只留被测服务 | 多一个空闲 JVM 影响不大，但压测对象累积会 |
| 压测对象 | 每轮结束删掉 | 否则 storage 体积线性增长 |
| 重复次数 | 同档 3 次取中位数 | 单次噪声可达数倍，见第四节与第十节 |
| 临时文件 | 记下所在盘剩余 | `bench_upload.py` 在 `%TEMP%`（C 盘）生成待传文件 |

## 四、首轮基线（LOCAL 后端）

环境：i7-12700H / 16 GB / D 盘 32 GB 可用（清理后）/ 单 JVM / JDK 17.0.19。

512 MB，103 个分片，16 并发，跑 3 次：

| 轮次 | 墙钟 | 上传阶段 | 合并阶段 | 上传阶段吞吐 |
| :--- | ---: | ---: | ---: | ---: |
| 1 | 2.97 s | 0.77 s | 2157 ms | 665 MB/s |
| 2 | 2.90 s | 0.69 s | 2171 ms | 743 MB/s |
| 3 | 2.99 s | 0.69 s | 2200 ms | 743 MB/s |
| **中位数** | **2.97 s** | **0.69 s** | **2171 ms** | **743 MB/s** |

有效吞吐（含 init 与合并）177 MB/s。合并阶段占了墙钟的 73%。

## 五、限流到底花掉多少

另起一个实例（18082）把 `rate-limit.chunk-concurrency` 从 12 放宽到 200，其余配置一致，同机同时段对照：

| 实例 | 分片并发上限 | 上传阶段 | 重试次数 |
| :--- | ---: | ---: | ---: |
| 18081 | 12 | 0.69 / 0.77 s | 9 次 / 103 片 |
| 18082 | 200 | 0.69 / 0.75 s | 0 |

**结论：限流对吞吐的影响在当前量级下不可测。** 它的代价只是超并发部分的排队重试（9/103 ≈ 8.7% 的分片多跑一次），而这些重试发生在 16 并发、每次约 50 ms 退避的量级，落进合并阶段的时间窗里看不出来。

顺带否掉一个直觉：限流的「12」限制的是**同时在飞的分片请求数**，不是吞吐。把并发压到 12 以内，一次都不会被拒。

## 六、瓶颈在磁盘 I/O，不在 CPU

裸设备测（同一块 D 盘，5 MB 块 × 103）：

| 操作 | 吞吐 |
| :--- | ---: |
| 顺序写（含 fsync） | 1717 MB/s |
| 顺序读 | 636 MB/s |

对照合并阶段：2171 ms 内要完成「读 103 个分片 + 写 1 个对象 + 回读整文件算 MD5」，I/O 总量约 1.5 GB，聚合 707 MB/s，正好压在**读速 636 MB/s** 附近。

所以 M1 的判断成立且原因更清楚：**合并慢是因为同一份数据被读了两遍**（拼装一遍、校验 md5 再读一遍），不是 CPU 不够。`storage.verify-merged-md5` 在本地方盘上省不掉这次回读，只有在能给产物指纹的后端（S3 的 multipart ETag）才能真正跳过。

## 七、可外推性判定

| 后端 | 哪些数字可信 | 哪些不可外推 |
| :--- | :--- | :--- |
| LOCAL | 全部（就是真实磁盘行为） | — |
| S3Mock | 相对差异（换后端前后的结构变化） | **绝对吞吐、合并耗时**。它的 `CompleteMultipartUpload` 在本地真拼字节（约 50 MB/s），真实 S3 只改元数据 |
| 真实 S3 | — | 本机没有，未测 |

写简历或文档时，S3 侧只能表述「合并从应用侧搬运变成存储端拼接，应用进程不再碰字节」，不能写成「S3 合并更快」。

## 九、限流对秒传 QPS 的封顶（新发现）

在**默认配置**（`init-per-minute: 120`）下重跑 200 次 / 32 并发：

```
HTTP 分布 {200: 200}
业务码分布 {0: 60, 1011: 140}
```

120 次全在窗口内通过，其余 140 次被拒。前一批 60 次是上一条命令用掉的额度，正好解释「60 通过」这个数字。

所以：**秒传 QPS 在默认配置下被硬性钉在 120 次/分钟/用户**，这是 `max-active-sessions` 之外的第二道闸。M1 的 253 QPS 是限流上线前的接口能力，两者不是同一个口径。简历或答辩讲这个数字必须带条件：

> 秒传接口单机 222–303 QPS（32 并发、关闭限流）；生产配置下按用户限 120 次/分钟。

顺带修了压测脚本一个会误导排查的缺陷：`do_instant` 里 `res.get("data", {}).get("instant")` 在错误响应（`data` 为 `null`）时抛 `AttributeError`，**把「有请求失败」伪装成脚本崩溃**，看不到业务码分布。改为 `(res.get("data") or {})`，并新增业务码直方图。

## 十、S3 后端同表（S3Mock，512 MB / 12 并发）

| 轮次 | 墙钟 | 上传阶段 | 合并阶段 | 有效吞吐 |
| :--- | ---: | ---: | ---: | ---: |
| 1 | 12.01 s | 3.66 s | 7897 ms | 42.6 MB/s |
| 2 | 12.74 s | 3.04 s | 9666 ms | 40.2 MB/s |

与 LOCAL 的差异有两处，**都归因于 S3Mock 而非 S3 协议**：

1. 上传阶段慢 6 倍（3.0 s vs 0.52 s）：每个分片多一跳 HTTP + S3Mock 自己写盘，等于同一份数据写两遍。
2. 合并慢 4 倍（7.9–9.7 s vs 1.9 s）：`CompleteMultipartUpload` 在本地真的把 103 个 part 拼成对象，而真实 S3 只改元数据。

结论不变：**S3 侧的绝对数字不进简历**，只能写「应用进程不再参与合并搬运」。
