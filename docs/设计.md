# 文件存储服务 · 设计文档

> 目标：一个能讲 20 分钟、能被追问三层不崩的后端项目。
> 不追求功能多，追求每个技术点都有可解释的取舍和可测量的数字。

## 一、边界

先把不做的事定死，避免项目失控。

| 做 | 不做 |
| :--- | :--- |
| 分片上传、断点续传、秒传 | 用户体系（一个写死的测试用户 + 简单 JWT 即可） |
| 并发安全的分片合并 | 图片压缩、视频转码、在线预览 |
| 存储层抽象（本地磁盘 + S3 兼容对象存储双实现） | 集群部署、分库分表、跨机房 |
| 上传进度查询、文件元数据管理 | 前端精雕细琢（能演示就行） |
| 上传限流、配额、过期会话清理 | 任何 AI 功能 |

**砍掉用户体系是有意的**：面试官关心的是并发、事务、幂等、存储设计，多一个登录注册不会加分，只会拖两周。

## 二、领域模型

四张表，两个层次：

```
upload_task（会话）  1 ── n  upload_chunk（分片）
        │
        │ 合并完成后产生
        ▼
file_info（物理文件，内容去重）  1 ── n  user_file（用户文件）
```

| 表 | 职责 | 关键约束 |
| :--- | :--- | :--- |
| `upload_task` | 一次上传一个会话，承载状态机 | `uk_upload_id` |
| `upload_chunk` | 分片是否已落盘 | `uk(upload_id, chunk_index)` |
| `file_info` | 物理文件，相同内容只存一份 | `uk(file_md5, file_size)` |
| `user_file` | 用户视角的目录项 | 不设唯一约束 |

完整 DDL 见 `sql/schema.sql`。

**为什么物理层和用户层要拆开**：秒传的本质是"内容已存在，只需新增一条引用"。如果只有一张表，同一份文件被三个人上传就要存三份物理副本，或者被迫做「同用户才算秒传」的阉割版。拆开后 `ref_count` 就能表达"这份物理文件被几个人引用"，删除时减到 0 才真正删对象存储里的文件——这是一个能顺着问三层的设计点。

代价也要说清：跨用户去重意味着 A 删除文件后，B 仍然能下载（因为引用还在），但 A 的"删除"语义变成了"移除自己的引用"。如果业务要求"我删了就是删了"，就得放弃全局去重，把 `uk` 改成 `(file_md5, file_size, owner_id)`。**这两条路要在面试时主动讲出来，而不是等被问。**

## 三、三个核心流程

### 3.1 初始化（含秒传判定）

```
POST /api/upload/init  { fileName, fileSize, fileMd5, chunkSize? }
```

1. 按 `(fileMd5, fileSize)` 查 `file_info`，且 `status = 1`（可用）
2. **命中** → 事务内 `ref_count + 1` + 插 `user_file` → 直接返回 `{ instant: true, fileId }`
3. **未命中** → 查 `upload_task` 是否有同 `(user_id, fileMd5, fileSize)` 的未完成会话
   - 有 → 直接复用该 `uploadId`，返回已上传分片列表（这就是断点续传）
   - 无 → 新建会话，`chunkTotal = ceil(fileSize / chunkSize)`，返回 `uploadId`

**为什么秒传要校验 size 而不只校验 MD5**：MD5 存在碰撞可能（构造碰撞已有公开方法），单靠 MD5 会把攻击者构造的恶意文件误判为"已存在"从而直接给出去。`(md5, size)` 双约束把碰撞门槛提高到实际不可行。若要更严，秒传命中后仍可要求客户端上传首尾分片做抽样校验。

### 3.2 分片上传

```
PUT /api/upload/{uploadId}/chunk/{index}   body = 原始字节
```

- 先落对象存储（临时前缀 `tmp/{uploadId}/{index}`），成功后再写 `upload_chunk`
- 写 `upload_chunk` 用 `INSERT ... ON DUPLICATE KEY UPDATE`，**网络重试导致同一分片重复提交时不会报错也不会重复计数**
- 会话 `status` 保持 1（上传中），每次分片成功后刷新 `expire_at`

顺序很重要：**先写存储再写数据库**。反过来的话，数据库说有分片但对象不存在，合并时会拼出空洞文件。

### 3.3 合并（全项目最需要讲清楚的地方）

```
POST /api/upload/{uploadId}/complete
```

三层保护，缺一层都能在压测里被打穿：

| 层 | 手段 | 防的是什么 |
| :--- | :--- | :--- |
| 1 | `UPDATE upload_task SET status=2 WHERE upload_id=? AND status=1` | 应用层 CAS，只有一个请求能进入合并 |
| 2 | Redis 分布式锁 `lock:upload:{uploadId}`，TTL 30s | 减少无效竞争，避免多实例同时打存储 |
| 3 | `uk(file_md5, file_size)` 唯一索引 | 兜底：锁失效 / 锁超时 / 应用重启后仍不会产生两条物理记录 |

**为什么锁之外还要唯一索引**：锁是会坏的——Redis 主从切换丢锁、GC 停顿导致 TTL 先于业务完成、进程被 kill。唯一索引是最后一道由数据库保证的防线。合并事务里若捕获 `DuplicateKeyException`，说明别的请求已经写成功，直接查出来复用 `fileId` 并把自己这次合并产生的临时对象删掉。

合并步骤：

1. 校验分片完整性：`count(upload_chunk where status=1) == chunk_total`，不等则返回 400 并告知缺失索引
2. 逐片按顺序聚合为最终对象：本地实现用 `FileChannel` 顺序拼接；S3 实现走标准 `CompleteMultipartUpload`，**不用 MinIO 私有的 `composeObject`** —— 那是 MinIO 扩展，换成其他 S3 服务就是运行时错误
3. 写 `file_info`（`status = 1`）
4. 事务内插 `user_file`，更新会话 `status = 3`
5. 异步删除 `tmp/{uploadId}/` 下的临时分片

`object_key` 用 `md5[0:2]/md5[2:]` 两级目录，避免所有对象挤在同一个前缀下造成的元数据热点。

## 四、接口契约

| 方法 | 路径 | 说明 | 幂等 |
| :--- | :--- | :--- | :--- |
| POST | `/api/upload/init` | 初始化会话 / 秒传判定 | 是（同 md5+size 复用会话） |
| GET | `/api/upload/{uploadId}` | 查询会话与已上传分片 | 是 |
| PUT | `/api/upload/{uploadId}/chunk/{index}` | 上传单个分片 | 是（`on duplicate key update`） |
| POST | `/api/upload/{uploadId}/complete` | 合并 | 是（三层保护） |
| DELETE | `/api/upload/{uploadId}` | 取消上传，清临时对象 | 是 |
| GET | `/api/file/list` | 当前用户的文件列表 | 是 |
| GET | `/api/file/{userFileId}` | 单个文件元信息 | 是 |
| GET | `/api/file/{userFileId}/download` | 下载，支持 Range / ETag | 是 |
| GET | `/api/file/{userFileId}/url` | 预签名直链（M2，仅 S3 实现有） | 是 |
| DELETE | `/api/file/{userFileId}` | 删除（引用减一） | 是 |

上传类接口统一返回 `{ "code": 0, "msg": "ok", "data": {...} }`；下载接口是例外，详见 4.1。

### 4.1 下载（唯一直接写 HTTP 响应的接口）

下载的消费者是浏览器与下载工具，不是业务前端，所以它必须服从 HTTP 语义而不是项目自定义的 `code`：

| 场景 | 状态码 | 关键响应头 |
| :--- | :--- | :--- |
| 完整下载 | 200 | `Content-Length`、`Accept-Ranges: bytes`、`ETag` |
| 区间下载 | 206 | `Content-Range: bytes start-end/total` |
| 客户端缓存仍有效 | 304 | `ETag`，无 body |
| 区间越界 | 416 | `Content-Range: bytes */total` |

三个设计点：

1. **ETag 直接用整文件 MD5**。内容按 MD5 寻址，MD5 不变即内容不变，不需要额外的版本号或 mtime，304 命中率天然高。
2. **只支持单区间**。多区间要求 body 用 `multipart/byteranges` 拼接，客户端几乎不用，RFC 7233 也允许忽略 Range 返回全量，所以多区间直接退化为 200。
3. **校验必须在写第一个字节之前完成**。响应一旦开始流出就提交了，之后出错只能得到截断的坏文件，无法再返回 JSON。因此没有用 `StreamingResponseBody`，而是手动控制写出时机，并把 `storage.openRange(key, offset, length)` 的区间长度写进抽象接口签名——本地实现靠 `LimitedInputStream` 截断，S3 实现靠 Range GET，行为才一致。

错误响应也走真实状态码，这是与上传接口唯一的行为差异：全局异常处理统一返回 HTTP 200 + 业务码，对 JSON 接口没问题，但浏览器点下载链接时 200 就是「下载成功」，会把错误 JSON 存成一个文件。所以下载方法自己 `writeError`，`ResultCode` 里 4xx/5xx 段的取值本就与 HTTP 对齐（404/403/413），直接映射；`1xxx` 的存储错误映射为 500。已知代价：`/api/file/list` 与 `/api/file/{id}` 仍是 HTTP 200 + 业务码，与下载接口不一致——这是刻意的，前者消费者是前端代码，后者是浏览器与下载器。

越权访问返回 **404 而不是 403**：403 等于确认「这个 ID 存在，只是不属于你」，配合自增 ID 就能把他人文件数量与上传节奏枚举出来。

### 4.2 删除与引用计数

删除接口删的是**引用**，不是数据。物理对象要等最后一个引用释放才消失。这条规则本身简单，难的是三个并发缝隙：

**缝隙一：重复删除会重复扣减。**
用户连点两次、客户端重试、网络超时后重发，都会让同一个 `userFileId` 被删两次。如果直接 `ref_count - 1`，两次调用减两次，别人还在用的文件会被误判归零而删掉——这是引用计数最常见的翻车方式。解法是把标记与扣减绑成一个 CAS：

```sql
UPDATE user_file SET status = 2
 WHERE id = ? AND user_id = ? AND status = 1;   -- 影响行数 0 就直接返回 alreadyDeleted
```

**缝隙二：「判断归零」与「标记删除」之间能插进一次秒传。**
如果先 `SELECT ref_count` 判断等于 1、再单独 `UPDATE` 标记删除，中间那段窗口里另一个请求秒传成功把计数加回 2，紧接着我们删掉物理对象，那条新引用就指向了不存在的文件。解法是把减与判定合成一条：

```sql
UPDATE file_info SET ref_count = ref_count - 1,
                     status = IF(ref_count = 0, 2, status)
 WHERE id = ? AND ref_count > 0;
```

赋值顺序是有意的：MySQL 的 `SET` 从左到右求值且用的是已更新的值，所以先减、再判断 `ref_count = 0`，读到的正是减完之后的结果。行锁保证这两步之间没有别的写入插进来。`ref_count > 0` 是兜底，防止计数被减成负数。

**缝隙三：物理对象删早了无法恢复。**
对象的删除必须放到事务提交之后（`TransactionSynchronization#afterCommit`）。反过来做——先删对象再提交——一旦事务回滚，数据库里记录还是「可用」，磁盘上文件却没了，用户能看到它、能点下载、拿到的却是 404，且没有任何自愈机制。代价是 `afterCommit` 已脱离事务，删对象失败只能记日志，留下 `status=2` 但对象仍在的孤儿记录，需要后续扫描清理。

**还有一处必须一起改：复活。**
秒传判定只认 `status=1`，所以「最后一个引用被删」与「同内容重新上传」撞在一起时，合并会走到唯一索引冲突分支并拿到一条 `status=2` 的记录。此时物理对象可能刚被删掉，但重新合并出的文件落在同一个 `objectKey` 上（`objectKey` 由 md5 决定），等于顺手把对象恢复了，记录也该改回可用。`revive` 用 `status=2` 作 CAS 条件，避免两个请求同时复活时重复加计数。

**已知局限：秒传 + 内容哈希 = 可探测文件是否存在。**
知道某个文件的 MD5 与大小，就能通过秒传接口确认服务端有没有这份内容——这是国内网盘秒传功能的通病。本项目的定位是内部存储服务，用户体系接入后应按用户隔离秒传判定（`uk` 加 `owner_id`），或对秒传命中只返回「已存在」而不直接建引用。M1 不在范围内，留作已知问题。

## 五、状态机

`upload_task.status`

```
0 初始化 ──> 1 上传中 ──> 2 合并中 ──> 3 成功
                │             │
                │             └──> 4 失败（retry_count < 3 时可回 1 重试）
                ├──> 5 已取消
                └──> 6 已过期（定时任务：status in (0,1) and expire_at < now）
```

只允许单向推进，任何状态回退都必须经过显式接口。**状态只能由 SQL 条件更新驱动，不允许"先 select 判断再 update"**——那是最典型的并发漏洞。

## 六、五个必须能讲清的取舍

### 1. 分片为什么是 5 MB

三个约束共同把它夹在中间：

- **下限**：S3 multipart 规范规定除最后一片外每片不小于 5 MB（AWS S3 的硬约束，MinIO / SeaweedFS 等实现遵循同一规范），低于此值无法走原生分片合并
- **上限方向**：片越大，网络抖动时重传代价越高（10 MB 片断在第 9 MB，要重传 10 MB）
- **数量方向**：片越小，请求数与 `upload_chunk` 行数越多，1 GB 用 1 MB 片就是 1000 次请求

5 MB 时 1 GB 文件 = 200 片，断点粒度 5 MB，200 次请求在 8 并发下可控。**这个数字不是拍脑袋，是被存储层下限倒推出来的。**

### 2. MD5 计算才是真正的瓶颈

1 GB 文件在前端做全量哈希，`Crypto.subtle` 没有流式接口，只能整块读进内存 → 内存峰值 1 GB，移动端直接崩，耗时 2–4 s。

两条解法，要能说清各自代价：

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| 增量哈希 | Web Worker + `spark-md5` 分块流式计算 | 内存平稳，但要多引入 30 KB 库 |
| 抽样哈希 | 首 2 MB + 中 2 MB + 尾 2 MB + 文件大小 | 秒级出结果，但有极小碰撞概率 |

实际做法：抽样哈希只用于**判定要不要走秒传**，命中后仍以文件大小做第二重校验；对安全敏感的场景再加一次服务端全量校验。

### 3. 为什么先写存储再写数据库

数据库写成功、存储写失败 → 数据库里有一条指向不存在对象的分片记录 → 合并时"分片齐了"但拼出来的文件缺块。
反过来的失败（存储有、库里没有）只是孤儿对象，定时任务扫掉即可。**不一致要往"可清理"的方向倒。**

### 4. 限流放在哪一层

按用户维度在网关层做令牌桶（`user_id` 为 key，Redis 计数），限制的是**并发分片数**而不是 QPS。因为一次上传天然产生 200 个请求，用 QPS 限流会把正常上传误杀。

### 5. 存储抽象分两层，第二层才是真问题

第一层是「换实现」：注入一个 `FileStorage`，`storage.type` 决定是本地还是 S3，业务代码零改动。
第二层是「多实现共存」：数据是持久的，配置是易变的，切后端的那一刻老数据仍留在老后端，
所以读与删必须按 `file_info.storage_type` 路由，写入才按配置。

只做第一层时，删错后端的后果是静默的数据丢失——对象键由内容 MD5 决定，两个后端天然可能同键。
细节见 [M2-多后端路由.md](M2-多后端路由.md)。

## 七、压测结果（2026-10-25 实测）

环境：i7-12700H（14C20T）/ 16 GB / Micron 2450 NVMe / JDK 17 / G1GC。客户端与服务端同机，走本地回环，所以吞吐是**上限参考**——真实网络下客户端带宽会先成为瓶颈。完整数据表见 README。

| 场景 | 参数 | 计划取的数 | 实测 |
| :--- | :--- | :--- | :--- |
| 分级上传 | 16 MB → 1 GB，并发 1/4/8/16 | 总耗时、吞吐、P99 | 1 GB 墙钟 5.84 s，有效吞吐 175.3 MB/s，上传阶段 999 MB/s，P99 分片 102 ms |
| 大文件上传 | 1 GB / 5 MB 分片 / 并发 16 | 同 | 205 分片，上传阶段 1.03 s，合并 4776 ms |
| 秒传 | 200 次 init / 32 并发 | P99、`file_info` 行数 | 253 QPS，P50/P95/P99 = 103/140/154 ms，`file_info` **1 条**，`ref_count` **201** 精确 |
| 合并并发 | 20 并发 complete | 成功数、是否重复插入 | 物理合并 **1 次**，19 次拿到 `reused=true`，失败 0，`file_info` 1 条 |
| 断点续传 | 传完部分后重连 | 剩余分片数、重传字节 | init 返回同一 uploadId 与已传下标，只补缺失分片 |
| 慢网络 | 客户端限速 | 超时率、重试 | **未做**，M1 不覆盖，列入 M3 |

三张关键表：

**瓶颈在合并不在上传**

| 文件 | 上传占比 | 合并占比 |
| :--- | ---: | ---: |
| 16 MB | 14% | 48% |
| 256 MB | 23% | 75% |
| 1 GB | 18% | 82% |

**`storage.verify-merged-md5` 对照（同一 1 GB 文件）**

| 配置 | 合并耗时 | 有效吞吐 |
| :--- | ---: | ---: |
| `true`（当时默认） | 4776 ms | 175.3 MB/s |
| `false` | 2518 ms | 266.9 MB/s |

差 47%，就是一次 1 GB 全量读的成本。默认保留，因为它是唯一生效的端到端完整性校验。

> M2 起这个开关改成三态 `auto` / `always` / `never`，默认 `auto`：S3 后端用 ETag 指纹校验，不再全量读回。上面的 `true`/`false` 是 M1 纯本地时期的实测，保留作为历史对照，不要和 M2 的数值混用。见 `docs/M2-S3存储实现.md`。

**堆占用与文件大小无关**

| 文件 | Eden 峰值 | Old 峰值 | Young GC | Full GC |
| :--- | ---: | ---: | ---: | ---: |
| 512 MB | 24 MB | 28 MB（恒定） | 0 次新增 | 0 |
| 1 GB | 20 MB | 34 MB | 4 次 | 0 |

工具：`scripts/bench_upload.py`（upload / instant）、`scripts/bench_merge_race.py`（合并竞态）。均为标准库实现，无第三方依赖。
**简历上的数字必须来自这里，不许估算。**

## 八、排期（2026-10-21 起，四周交付）

**前提**：不参加国考，10 月下旬起为全职投入窗口；春招（2027 年 3–4 月）是唯一大窗口，也是唯一一次机会。

### 排期规则

1. **最小单位是一天，不是一周** —— 当天开工时不需要再做决策。
2. **按风险排序，不按模块排序** —— 最可能失败的部分（合并并发、MinIO 接入）先做，别留到最后。
3. **留缓冲** —— 四周的活按三周排，空出的一周给返工、报错和踩环境坑，不给新功能。
4. **止损点提前写死** —— 到点没达标就砍功能，不延期。延期会挤压后面的八股期，那才是真正的失分项。

## 九、验收清单

- [ ] 1 GB 文件在 8 并发下上传成功，且合并后文件 MD5 与原始一致（这是唯一可信的正确性标准）
- [ ] 同一文件重复上传走秒传，响应 < 200 ms
- [ ] 200 并发 init 后 `select count(*) from file_info where file_md5=?` 结果为 1
- [ ] 20 并发 complete 只成功一次，无重复物理文件
- [ ] 上传中断后重连，只补传缺失分片
- [ ] 把 `storage.type` 从 `local` 改成 `minio` 重启即可切换，业务代码零改动
- [ ] `ref_count` 归零后物理对象被清理，且有日志可追溯

## 附录 · 三个必答题的准备方式

| 问题 | 不要这样答 | 这样答 |
| :--- | :--- | :--- |
| 为什么分片？ | "因为文件大" | 单请求超时、服务端内存溢出、失败无法续传——三个具体的失败模式 |
| 秒传怎么防误判？ | "算 MD5 就行" | MD5 有构造碰撞，必须加文件大小；更高要求再加首尾抽样或全量校验 |
| 合并并发怎么办？ | "加个锁" | 状态机 CAS + Redis 锁 + 唯一索引三层，并说清为什么锁不可靠 |

面试官追问到第三层时，能不能说出"锁会因 GC 停顿或主从切换失效"，是这道题的分水岭。
