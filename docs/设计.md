## 二、领域模型

四张表，两个层次：

```
upload_task（会话）  1 ── n  upload_chunk（分片）
        │
        │ 合并完成后产生
        ▼
file_info（物理文件，内容去重）  1 ── n  user_file（用户文件）
```

| 表 | 职责 | 关键约束 |
| :--- | :--- | :--- |
| `upload_task` | 一次上传一个会话，承载状态机 | `uk_upload_id` |
| `upload_chunk` | 分片是否已落盘 | `uk(upload_id, chunk_index)` |
| `file_info` | 物理文件，相同内容只存一份 | `uk(file_md5, file_size)` |
| `user_file` | 用户视角的目录项 | 不设唯一约束 |

完整 DDL 见 `sql/schema.sql`。

**为什么物理层和用户层要拆开**：秒传的本质是"内容已存在，只需新增一条引用"。如果只有一张表，同一份文件被三个人上传就要存三份物理副本，或者被迫做「同用户才算秒传」的阉割版。拆开后 `ref_count` 就能表达"这份物理文件被几个人引用"，删除时减到 0 才真正删对象存储里的文件——这是一个能顺着问三层的设计点。

代价也要说清：跨用户去重意味着 A 删除文件后，B 仍然能下载（因为引用还在），但 A 的"删除"语义变成了"移除自己的引用"。如果业务要求"我删了就是删了"，就得放弃全局去重，把 `uk` 改成 `(file_md5, file_size, owner_id)`。**这两条路要在面试时主动讲出来，而不是等被问。**

## 三、三个核心流程

### 3.1 初始化（含秒传判定）

```
POST /api/upload/init  { fileName, fileSize, fileMd5, chunkSize? }
```

1. 按 `(fileMd5, fileSize)` 查 `file_info`，且 `status = 1`（可用）
2. **命中** → 事务内 `ref_count + 1` + 插 `user_file` → 直接返回 `{ instant: true, fileId }`
3. **未命中** → 查 `upload_task` 是否有同 `(user_id, fileMd5, fileSize)` 的未完成会话
   - 有 → 直接复用该 `uploadId`，返回已上传分片列表（这就是断点续传）
   - 无 → 新建会话，`chunkTotal = ceil(fileSize / chunkSize)`，返回 `uploadId`

**为什么秒传要校验 size 而不只校验 MD5**：MD5 存在碰撞可能（构造碰撞已有公开方法），单靠 MD5 会把攻击者构造的恶意文件误判为"已存在"从而直接给出去。`(md5, size)` 双约束把碰撞门槛提高到实际不可行。若要更严，秒传命中后仍可要求客户端上传首尾分片做抽样校验。

### 3.2 分片上传

```
PUT /api/upload/{uploadId}/chunk/{index}   body = 原始字节
```

- 先落对象存储（临时前缀 `tmp/{uploadId}/{index}`），成功后再写 `upload_chunk`
- 写 `upload_chunk` 用 `INSERT ... ON DUPLICATE KEY UPDATE`，**网络重试导致同一分片重复提交时不会报错也不会重复计数**
- 会话 `status` 保持 1（上传中），每次分片成功后刷新 `expire_at`

顺序很重要：**先写存储再写数据库**。反过来的话，数据库说有分片但对象不存在，合并时会拼出空洞文件。

### 3.3 合并（全项目最需要讲清楚的地方）

```
POST /api/upload/{uploadId}/complete
```

三层保护，缺一层都能在压测里被打穿：

| 层 | 手段 | 防的是什么 |
| :--- | :--- | :--- |
| 1 | `UPDATE upload_task SET status=2 WHERE upload_id=? AND status=1` | 应用层 CAS，只有一个请求能进入合并 |
| 2 | Redis 分布式锁 `lock:upload:{uploadId}`，TTL 30s | 减少无效竞争，避免多实例同时打存储 |
| 3 | `uk(file_md5, file_size)` 唯一索引 | 兜底：锁失效 / 锁超时 / 应用重启后仍不会产生两条物理记录 |

**为什么锁之外还要唯一索引**：锁是会坏的——Redis 主从切换丢锁、GC 停顿导致 TTL 先于业务完成、进程被 kill。唯一索引是最后一道由数据库保证的防线。合并事务里若捕获 `DuplicateKeyException`，说明别的请求已经写成功，直接查出来复用 `fileId` 并把自己这次合并产生的临时对象删掉。

合并步骤：

1. 校验分片完整性：`count(upload_chunk where status=1) == chunk_total`，不等则返回 400 并告知缺失索引
2. 逐片按顺序聚合为最终对象：本地实现用 `FileChannel` 顺序拼接；S3 实现走标准 `CompleteMultipartUpload`，**不用 MinIO 私有的 `composeObject`** —— 那是 MinIO 扩展，换成其他 S3 服务就是运行时错误
3. 写 `file_info`（`status = 1`）
4. 事务内插 `user_file`，更新会话 `status = 3`
5. 异步删除 `tmp/{uploadId}/` 下的临时分片

`object_key` 用 `md5[0:2]/md5[2:]` 两级目录，避免所有对象挤在同一个前缀下造成的元数据热点。

## 四、接口契约

| 方法 | 路径 | 说明 | 幂等 |
| :--- | :--- | :--- | :--- |
| POST | `/api/upload/init` | 初始化会话 / 秒传判定 | 是（同 md5+size 复用会话） |
| GET | `/api/upload/{uploadId}` | 查询会话与已上传分片 | 是 |
| PUT | `/api/upload/{uploadId}/chunk/{index}` | 上传单个分片 | 是（`on duplicate key update`） |
| POST | `/api/upload/{uploadId}/complete` | 合并 | 是（三层保护） |
| DELETE | `/api/upload/{uploadId}` | 取消上传，清临时对象 | 是 |
| GET | `/api/file/{fileId}/url` | 获取下载地址（预签名 / 直链） | 是 |
| DELETE | `/api/file/{userFileId}` | 删除（引用减一） | 是 |

统一响应：`{ "code": 0, "msg": "ok", "data": {...} }`，错误码分段：`1xxx` 参数、`2xxx` 会话状态、`3xxx` 存储异常、`4xxx` 限流。

## 五、状态机

`upload_task.status`

```
0 初始化 ──> 1 上传中 ──> 2 合并中 ──> 3 成功
                │             │
                │             └──> 4 失败（retry_count < 3 时可回 1 重试）
                ├──> 5 已取消
                └──> 6 已过期（定时任务：status in (0,1) and expire_at < now）
```

只允许单向推进，任何状态回退都必须经过显式接口。**状态只能由 SQL 条件更新驱动，不允许"先 select 判断再 update"**——那是最典型的并发漏洞。

## 六、四个必须能讲清的取舍

### 1. 分片为什么是 5 MB

三个约束共同把它夹在中间：

- **下限**：S3 multipart 规范规定除最后一片外每片不小于 5 MB（AWS S3 的硬约束，MinIO / SeaweedFS 等实现遵循同一规范），低于此值无法走原生分片合并
- **上限方向**：片越大，网络抖动时重传代价越高（10 MB 片断在第 9 MB，要重传 10 MB）
- **数量方向**：片越小，请求数与 `upload_chunk` 行数越多，1 GB 用 1 MB 片就是 1000 次请求

5 MB 时 1 GB 文件 = 200 片，断点粒度 5 MB，200 次请求在 8 并发下可控。**这个数字不是拍脑袋，是被存储层下限倒推出来的。**

### 2. MD5 计算才是真正的瓶颈

1 GB 文件在前端做全量哈希，`Crypto.subtle` 没有流式接口，只能整块读进内存 → 内存峰值 1 GB，移动端直接崩，耗时 2–4 s。

两条解法，要能说清各自代价：

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| 增量哈希 | Web Worker + `spark-md5` 分块流式计算 | 内存平稳，但要多引入 30 KB 库 |
| 抽样哈希 | 首 2 MB + 中 2 MB + 尾 2 MB + 文件大小 | 秒级出结果，但有极小碰撞概率 |

实际做法：抽样哈希只用于**判定要不要走秒传**，命中后仍以文件大小做第二重校验；对安全敏感的场景再加一次服务端全量校验。

### 3. 为什么先写存储再写数据库

数据库写成功、存储写失败 → 数据库里有一条指向不存在对象的分片记录 → 合并时"分片齐了"但拼出来的文件缺块。
反过来的失败（存储有、库里没有）只是孤儿对象，定时任务扫掉即可。**不一致要往"可清理"的方向倒。**

### 4. 限流放在哪一层

按用户维度在网关层做令牌桶（`user_id` 为 key，Redis 计数），限制的是**并发分片数**而不是 QPS。因为一次上传天然产生 200 个请求，用 QPS 限流会把正常上传误杀。

## 九、验收清单

- [ ] 1 GB 文件在 8 并发下上传成功，且合并后文件 MD5 与原始一致（这是唯一可信的正确性标准）
- [ ] 同一文件重复上传走秒传，响应 < 200 ms
- [ ] 200 并发 init 后 `select count(*) from file_info where file_md5=?` 结果为 1
- [ ] 20 并发 complete 只成功一次，无重复物理文件
- [ ] 上传中断后重连，只补传缺失分片
- [ ] 把 `storage.type` 从 `local` 改成 `minio` 重启即可切换，业务代码零改动
- [ ] `ref_count` 归零后物理对象被清理，且有日志可追溯

## 附录 · 三个必答题的准备方式

| 问题 | 不要这样答 | 这样答 |
| :--- | :--- | :--- |
| 为什么分片？ | "因为文件大" | 单请求超时、服务端内存溢出、失败无法续传——三个具体的失败模式 |
| 秒传怎么防误判？ | "算 MD5 就行" | MD5 有构造碰撞，必须加文件大小；更高要求再加首尾抽样或全量校验 |
| 合并并发怎么办？ | "加个锁" | 状态机 CAS + Redis 锁 + 唯一索引三层，并说清为什么锁不可靠 |

面试官追问到第三层时，能不能说出"锁会因 GC 停顿或主从切换失效"，是这道题的分水岭。
